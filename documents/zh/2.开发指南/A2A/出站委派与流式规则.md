# 出站委派与流式规则

当你的 Agent（A）在工具里委派另一个远端 Agent（B）时，运行时需要决定：**远端 B 产生的消息要不要透传给最终客户端**，以及**哪一条作为委派结果回喂给 A 的模型**。本文描述这套对外可观测的行为契约与你需要做的配置，不涉及内部实现。

配置与整体调用链见 [A2A 开发指导](开发指导.md)。

## 两种模式

委派行为由中断上下文里的 `_stream_mode` 决定：

| 模式 | 触发 | 远端过程消息 → 客户端 | 回喂给 A 模型的内容 |
| --- | --- | --- | --- |
| **流式透传** | `_stream_mode = "sse"` | 每条原样透传 | 远端最终答案的正文 |
| **非流式**（默认） | 未设置 / 其它值 | 不透传 | 远端最终答案的正文 |

要点：

- 两种模式回喂给模型的都是**答案正文**，因此模型侧行为一致；差别只在于**客户端能否实时看到远端过程**。
- 流式透传下，最终答案会像普通流消息一样透传给客户端，**格式与其它流消息完全一致**——它不会因为要回喂模型而从客户端流里消失。
- 透传是显式开启的：不设置 `_stream_mode=sse` 就没有过程透传，客户端只会在委派结束后看到 A 消化远端结果后的输出。

## 如何开启透传

在触发委派的中断上下文里声明 `_stream_mode`：

```java
context = Map.of(
    "agentName", "agentb",
    "_interrupt_kind", "a2a_delegate",
    "_stream_mode", "sse"   // 省略即为非流式，无过程透传
);
```

仅当值精确等于字符串 `"sse"` 时才启用流式透传；空、缺省或任何其它值都按非流式处理。

## 客户端在流式模式下收到什么

远端每条流消息以统一信封透传，客户端收到的是信封的 JSON 文本：

```json
{ "type": "answer", "index": 3, "payload": { "content": "..." } }
```

- `type`：消息类型，普通中间片段与最终答案通过它区分，最终答案的 `type` 为 `"answer"`。
- `index`：消息序号。
- `payload`：消息负载，正文通常在 `content` 字段。

所有流消息（含最终答案）都用同一信封结构，客户端可以用统一逻辑解析，通过 `type == "answer"` 识别最终答案。

> 非流式模式下没有信封：委派结果是聚合后的纯文本，直接作为 A 的工具结果。因此「非流式结果看起来没有信封」是预期行为，不是缺陷。

## 答案如何被识别与回喂

运行时依据信封自身的 `type == "answer"` 识别最终答案，**不依赖任何额外的 metadata 标记**。识别到答案后，从其 `payload`（或信封顶层）按 `content` → `delta` → `output` → `response` 的顺序取第一段正文，作为委派结果回喂给 A 的模型。

对你的影响：

- 被委派的 Agent B **必须在结束时输出一条 `type == "answer"` 的消息**，否则运行时抽不到答案，A 的模型会收到空结果。
- 答案正文应放在 `content`/`delta`/`output`/`response` 之一。若正文放在其它字段，运行时会把整段信封 JSON 当作正文回喂，模型将收到一坨 JSON 而非纯文本。

## 中断与恢复

远端 B 需要更多输入时会返回 `INPUT_REQUIRED`，运行时向客户端抛出中断，等待下一轮同一 `conversationId` 的请求继续。恢复时会沿用首次委派的 `_stream_mode`：首次是流式则继续流式透传，否则继续非流式。

你无需手动维护任何恢复状态，只要下一轮请求带上相同的 `conversationId` 即可续接。

## 小结与注意事项

- 想让客户端实时看到远端过程：显式设置 `_stream_mode=sse`。
- 被委派 Agent 要输出 `type=answer` 的收尾消息，正文放在标准字段（`content`/`delta`/`output`/`response`）。
- 流式与非流式回喂模型的都是答案正文，切换模式不影响模型看到的内容，只影响客户端可见性。
