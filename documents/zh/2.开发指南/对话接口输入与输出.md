# 对话接口输入与输出

本文说明 Agent Runtime Java 对外提供的两种 REST Query 接口和 A2A JSON-RPC 接口，包括普通调用、SSE、业务中断恢复、并行工具输入关联，以及 A2A `parts.text` 与 `parts.data` 的使用边界。

## 接口总览

| 协议 | 接口 | 传输方式 | 用途 |
| --- | --- | --- | --- |
| REST | `POST /v1/query` | JSON 或 SSE | Servlet/MVC 应用的 Query 接口 |
| REST | `POST /v1/query/reactive` | JSON 或 SSE | WebFlux 应用的 Reactive Query 接口 |
| A2A | `POST /a2a`、`POST /a2a/` | JSON-RPC 或 JSON-RPC over SSE | 标准 A2A 消息、任务与中断恢复 |

`/v1/query` 和 `/v1/query/reactive` 使用相同的请求及响应模型。请求中的 `stream` 决定返回聚合 JSON 还是 SSE。兼容路径 `POST /query` 与 `/v1/query` 行为相同，但可通过配置关闭。

A2A 使用独立的 JSON-RPC 报文，不接受 REST `QueryRequest`。两类接口最终都会转换为 Runtime 内部的 `ServeRequest`，并经过同一个 `ServeOrchestrator`。

## REST Query 输入

### 请求字段

两种 REST Query 接口都接受 `QueryRequest`：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `conversation_id` | string | 是 | 无 | 会话标识；必须非空，多轮及中断恢复时保持不变 |
| `message` | string | 二选一 | 无 | 单轮简写；仅当 `messages` 为空时转换为一条 user 消息 |
| `messages` | array | 二选一 | `[]` | OpenAI 风格消息列表；Runtime 使用最后一条具有 `content` 的 user 消息作为本轮问题 |
| `stream` | boolean | 否 | `true` | `false` 返回聚合 JSON，`true` 返回 SSE |
| `user_id` | string | 否 | `anonymous` | 用户标识 |
| `space_id` | string | 否 | `default` | 空间标识 |
| `tenant_id` | string | 否 | 无 | 租户标识 |

网关可以使用 `X-User-ID`、`X-Space-ID` 和 `X-Tenant-ID` 请求头设置对应标识。请求头存在且非空时覆盖请求体中的值。

单消息请求示例：

```json
{
  "conversation_id": "conversation-001",
  "message": "Summarize the quarterly report.",
  "stream": false,
  "user_id": "user-001",
  "space_id": "finance"
}
```

消息列表请求示例：

```json
{
  "conversation_id": "conversation-001",
  "messages": [
    {
      "role": "user",
      "content": "My preferred currency is CNY."
    },
    {
      "role": "assistant",
      "content": "Understood."
    },
    {
      "role": "user",
      "content": "Review this expense claim."
    }
  ],
  "stream": true
}
```

不要同时依赖 `message` 和 `messages`。如果 `messages` 非空，`message` 不会覆盖它。

### 两种 REST 接口的选择

`POST /v1/query` 用于 Servlet/MVC 应用，支持 `stream=false` 和 `stream=true`。通常的 Spring Boot Servlet 应用直接使用此接口。

`POST /v1/query/reactive` 用于 WebFlux 应用，需要启用：

```yaml
openjiuwen:
  service:
    query:
      webflux:
        enabled: true
```

两个接口的 JSON 字段和 SSE 事件内容相同，客户端不应根据入口路径编写两套业务解析逻辑。

## REST Query 输出

### 非流式 JSON

`stream=false` 时返回 `QueryResponse`：

```json
{
  "result": {
    "role": "assistant",
    "content": "The claim is within policy."
  },
  "conversation_id": "conversation-001"
}
```

| 字段 | 说明 |
| --- | --- |
| `result` | 聚合后的 Agent 结果；通常包含 `role` 和 `content` |
| `conversation_id` | 请求中的会话标识 |
| `result._interrupt` | 可选；Agent 等待用户输入时返回的结构化中断信息 |

Agent 输出内容由具体 Agent 决定，因此 `result` 是开放对象。客户端至少应兼容 `content` 不存在或不是固定业务文本的情况。

### 流式 SSE

`stream=true` 时响应类型为 `text/event-stream`。每个 `data:` 行是一段独立 JSON，示例：

```text
data: {"type":"llm_output","index":0,"payload":{"content":"The claim"}}

data: {"type":"answer","index":1,"payload":{"output":"The claim is within policy."}}
```

REST SSE 直接输出 `QueryChunk.data`，不会再包一层 `{ "type": "chunk", "data": ... }`。常见 Agent Core 事件包括：

| `type` | 用途 |
| --- | --- |
| `llm_reasoning` | 模型推理过程，是否产生取决于模型和 Agent 配置 |
| `llm_output` | 模型增量输出或工具调用片段 |
| `llm_usage` | token、延迟等用量信息 |
| `answer` | Agent 最终答案 |
| `workflow_final` | WorkflowAgent 最终结果 |
| `__interaction__` | 业务中断，需要用户继续输入 |
| `error` | 执行错误信息 |

客户端应逐条解析 SSE 事件，并根据 `type` 分发；不要把整个 SSE 响应拼成一个 JSON，也不要假设每条事件都有相同的 `payload` 结构。

### REST 中断与恢复

非流式中断响应示例：

```json
{
  "result": {
    "role": "assistant",
    "content": "Approve this expense claim?",
    "_interrupt": {
      "type": "__interaction__",
      "message": "Approve this expense claim?",
      "toolCallId": "call_expense_001",
      "toolName": "manual_approval"
    }
  },
  "conversation_id": "conversation-001"
}
```

流式调用会通过 `type=__interaction__` 的 SSE 数据返回同类信息。

REST 恢复继续使用同一个 `conversation_id`，并把用户答复作为新一轮 `message`：

```json
{
  "conversation_id": "conversation-001",
  "message": "approved",
  "stream": false
}
```

REST `QueryRequest` 没有公开的 `taskId` 字段。Runtime 使用 `conversation_id` 和保存的会话状态恢复 REST 对话。对于只有一个待输入工具的远端委派，普通答复即可关联；需要分别回答多个并行远端工具时，应使用下文的 A2A `taskId + toolCallId` 定向恢复格式。

### REST 错误响应

常见错误形状：

```json
{
  "type": "error",
  "error": "conversation_id is required"
}
```

同步执行失败时返回 HTTP 500：

```json
{
  "type": "error",
  "code": "AGENT_EXECUTION_FAILED",
  "error": "agent execution failed",
  "conversation_id": "conversation-001"
}
```

Agent 尚未加载或没有可用 Handler 时返回 HTTP 503。流式执行发生错误后连接会结束，客户端应同时处理错误事件和连接关闭。

## A2A 输入

### SendMessage

非流式请求使用 `SendMessage`：

```json
{
  "jsonrpc": "2.0",
  "id": "request-001",
  "method": "SendMessage",
  "params": {
    "message": {
      "role": "ROLE_USER",
      "contextId": "context-001",
      "messageId": "message-001",
      "parts": [
        {
          "text": "Review expense claim EXP-001."
        }
      ]
    },
    "metadata": {
      "traceId": "trace-001"
    }
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `jsonrpc` | 是 | 固定为 `2.0` |
| `id` | 是 | 本次 JSON-RPC 请求标识；用于匹配请求和响应，不是任务 ID |
| `method` | 是 | `SendMessage`、`SendStreamingMessage` 或 `GetTask` |
| `params.message.role` | 否 | 默认 `ROLE_USER`；通常显式传入 |
| `params.message.contextId` | 建议 | 对话上下文；多轮及中断恢复时必须保持一致 |
| `params.message.taskId` | 恢复时必填 | 首轮由服务端创建的 A2A Task ID |
| `params.message.messageId` | 否 | 消息标识；省略时由 SDK 生成 |
| `params.message.parts` | 是 | 至少包含一个非空文本 Part |
| `params.metadata` | 否 | 请求级元数据，会传入 Runtime 编排层 |

A2A 标准定义了 `TextPart`、`DataPart` 和 `FilePart`。当前 Runtime 入站 Query 只消费 `parts[].text`，只有 `data` 或 `file` 的请求会被判定为没有可用文本。因此调用 Runtime 时应使用 `TextPart`；不要把用户问题序列化成 JSON 后放进 `data`。

### SendStreamingMessage

流式请求把 `method` 改为 `SendStreamingMessage`，消息结构不变：

```json
{
  "jsonrpc": "2.0",
  "id": "request-stream-001",
  "method": "SendStreamingMessage",
  "params": {
    "message": {
      "role": "ROLE_USER",
      "contextId": "context-stream-001",
      "parts": [
        {
          "text": "Review expense claim EXP-STREAM-001."
        }
      ]
    }
  }
}
```

客户端还应发送 `Accept: text/event-stream` 并持续读取连接。

## A2A 输出

### 非流式任务

`SendMessage` 返回单个 JSON-RPC 响应。完成任务示例：

```json
{
  "jsonrpc": "2.0",
  "id": "request-001",
  "result": {
    "task": {
      "id": "task-001",
      "contextId": "context-001",
      "status": {
        "state": "TASK_STATE_COMPLETED",
        "timestamp": "2026-07-26T08:00:00Z"
      },
      "artifacts": [
        {
          "artifactId": "artifact-001",
          "parts": [
            {
              "text": "Expense claim EXP-001 was approved."
            }
          ]
        }
      ],
      "history": []
    }
  }
}
```

任务 ID 位于 `result.task.id`，状态位于 `result.task.status.state`。不要把 JSON-RPC 的顶层 `id` 当作 Task ID。

### 流式任务

`SendStreamingMessage` 返回一系列具名 SSE 事件：

```text
event:jsonrpc
data:{"jsonrpc":"2.0","id":"request-stream-001","result":{"statusUpdate":{"taskId":"task-stream-001","status":{"state":"TASK_STATE_WORKING"},"contextId":"context-stream-001"}}}

event:jsonrpc
data:{"jsonrpc":"2.0","id":"request-stream-001","result":{"artifactUpdate":{"taskId":"task-stream-001","artifact":{"artifactId":"artifact-stream-001","parts":[{"data":{"type":"llm_output","index":0,"payload":{"content":"Review in progress"}}}]},"contextId":"context-stream-001"}}}

event:jsonrpc
data:{"jsonrpc":"2.0","id":"request-stream-001","result":{"artifactUpdate":{"taskId":"task-stream-001","artifact":{"artifactId":"artifact-stream-001","parts":[{"text":"Expense claim EXP-STREAM-001 was approved."}]},"contextId":"context-stream-001"}}}

event:jsonrpc
data:{"jsonrpc":"2.0","id":"request-stream-001","result":{"statusUpdate":{"taskId":"task-stream-001","status":{"state":"TASK_STATE_COMPLETED"},"contextId":"context-stream-001"}}}
```

每个 SSE `data:` 行都是完整 JSON-RPC 响应。示例中的第一个 `artifactUpdate` 通过 `parts[].data` 返回结构化中间事件，第二个 `artifactUpdate` 通过 `parts[].text` 返回最终业务文本。`result` 的具体事件通过成员名区分：

| 事件 | 说明 |
| --- | --- |
| `statusUpdate` | Task 状态变化；`taskId` 位于该对象内 |
| `artifactUpdate` | 增量 artifact；业务内容位于 `artifact.parts` |
| `task` | 某些响应直接携带完整 Task |
| `message` | 某些无 Task 的即时消息响应 |

客户端不应在收到第一个 artifact 时就判定任务完成，应等待 `TASK_STATE_COMPLETED`、`TASK_STATE_FAILED` 或 `TASK_STATE_INPUT_REQUIRED` 等终态状态事件。

### TextPart 与 DataPart

A2A `Part` 是联合类型。Runtime 按内容语义选择字段：

| Part | JSON 形状 | Runtime 输出用途 | 客户端处理 |
| --- | --- | --- | --- |
| `TextPart` | `{ "text": "..." }` | 最终 `answer`、`workflow_final` 解信封后的标量业务文本，以及人类可读状态 | 直接展示或拼接文本 |
| `DataPart` | `{ "data": { ... } }` | `llm_reasoning`、中间 `llm_output`、`llm_usage` 等结构化事件，以及解信封后的结构化最终结果 | 作为 JSON 对象处理；中间事件可按 `type` 分发，最终结果按业务字段读取 |
| `FilePart` | `{ "url": "..." }` 或 `{ "raw": "..." }` | 标准 A2A 文件内容；当前 Runtime Query 不主动生成 | 按标准 SDK 的 FilePart 处理 |

结构化事件示例：

```json
{
  "data": {
    "type": "llm_output",
    "index": 1,
    "payload": {
      "content": "Review in progress"
    }
  },
  "metadata": {
    "_remote_invocation": {
      "kind": "remote_agent_invocation",
      "toolCallId": "call_delegate_001",
      "target": "expense-agent",
      "phase": "RUNNING"
    }
  }
}
```

最终文本示例：

```json
{
  "text": "Expense claim EXP-001 was approved."
}
```

Workflow End 未配置文本模板且直接返回对象时，最终结果仍保持为结构化 `DataPart`，但外层
`workflow_final` 信封已被移除：

```json
{
  "data": {
    "claim_id": "EXP-001",
    "policy_status": "COMPLIANT",
    "auto_decision": "auto-approved"
  }
}
```

Runtime 在解开 `answer` 或 `workflow_final` 信封后，会在承载最终结果的 artifact 上添加
`metadata._agentcore_terminal: true`。该字段是 Runtime 内部使用的终态来源标识，用于在远端调用完成时
区分最终业务结果与此前的流式中间 artifact；它不属于 `parts.text` 或 `parts.data` 中的业务数据，客户端
不应依赖它表达业务语义。通用第三方 A2A Agent 无需添加该字段。

不要假设所有 `parts` 都有 `text`，也不要对 `text` 再尝试解析内部 JSON。使用标准 A2A SDK 时应按 Part 类型分支：

```java
for (Part<?> part : artifact.parts()) {
    if (part instanceof TextPart textPart) {
        consumeText(textPart.text());
    } else if (part instanceof DataPart dataPart) {
        consumeStructuredEvent(dataPart.data());
    } else if (part instanceof FilePart filePart) {
        consumeFile(filePart.file());
    }
}
```

标准 A2A SDK 会把 `{"text": ...}` 反序列化为 `TextPart`，把 `{"data": ...}` 反序列化为 `DataPart`。应用层仍需显式处理不同子类型，SDK 不会自动把 `DataPart` 转成文本。

## A2A 中断恢复

### 获取关联标识

任务需要用户输入时，状态变为 `TASK_STATE_INPUT_REQUIRED`。非流式响应中的关键结构如下：

```json
{
  "result": {
    "task": {
      "id": "task-approval-001",
      "contextId": "context-approval-001",
      "status": {
        "state": "TASK_STATE_INPUT_REQUIRED",
        "message": {
          "role": "ROLE_AGENT",
          "parts": [
            {
              "text": "Approve expense claim EXP-001?"
            }
          ],
          "metadata": {
            "_interrupt": {
              "message": "Approve expense claim EXP-001?",
              "items": [
                {
                  "toolCallId": "call_approval_001",
                  "toolName": "manual_approval",
                  "message": "Approve expense claim EXP-001?"
                }
              ]
            }
          }
        }
      }
    }
  }
}
```

流式响应中的相同信息位于 `result.statusUpdate`：

- `result.statusUpdate.taskId`
- `result.statusUpdate.contextId`
- `result.statusUpdate.status.state`
- `result.statusUpdate.status.message.metadata._interrupt.items[].toolCallId`

这三个标识用途不同：

| 标识 | 用途 |
| --- | --- |
| JSON-RPC `id` | 匹配一次 HTTP 请求和响应 |
| `contextId` | 标识对话上下文 |
| `taskId` | 标识需要恢复的 A2A Task |
| `toolCallId` | 标识该 Task 内等待输入的具体函数工具调用 |

### 单个待输入工具

恢复请求必须复用首轮的 `contextId` 和服务端返回的 `taskId`：

```json
{
  "jsonrpc": "2.0",
  "id": "request-approval-002",
  "method": "SendMessage",
  "params": {
    "message": {
      "role": "ROLE_USER",
      "contextId": "context-approval-001",
      "taskId": "task-approval-001",
      "parts": [
        {
          "text": "approved"
        }
      ]
    }
  }
}
```

只有一个待输入工具时可以省略 `toolCallId`。恢复请求可以继续使用 `SendMessage`，也可以使用 `SendStreamingMessage`；选择后者时恢复过程以 SSE 返回。

### 多个并行工具的定向恢复

同一 Task 内有多个工具同时等待输入时，仅提供一段无目标文本会产生 `REMOTE_TOOL_INPUT_TARGET_REQUIRED`。客户端必须为每个答复指定中断响应中的 `toolCallId`：

```json
{
  "jsonrpc": "2.0",
  "id": "request-batch-002",
  "method": "SendMessage",
  "params": {
    "message": {
      "role": "ROLE_USER",
      "contextId": "context-batch-001",
      "taskId": "task-batch-001",
      "parts": [
        {
          "text": "approved",
          "metadata": {
            "toolCallId": "call_approval_001"
          }
        },
        {
          "text": "Use tomorrow as the travel date.",
          "metadata": {
            "toolCallId": "call_travel_002"
          }
        }
      ]
    }
  }
}
```

定向恢复规则：

- `toolCallId` 来自服务端 `_interrupt.items[]`，不能由客户端自行生成。
- 一次请求可以只回答部分待输入工具；未回答的工具继续保持 `INPUT_REQUIRED`。
- 所有文本 Part 必须全部携带 `metadata.toolCallId`，不能混合定向与非定向 Part，否则返回 `REMOTE_TOOL_INPUT_TARGET_MIXED`。
- 多个具有相同 `toolCallId` 的连续文本 Part 会按出现顺序拼接。
- 未知 `toolCallId` 返回 `REMOTE_TOOL_INPUT_TARGET_UNKNOWN`；对非等待状态的工具重复输入返回 `REMOTE_TOOL_INPUT_STATE_CONFLICT`。
- 客户端提交的是标准 Part metadata。不要直接伪造 `runtime.parentTaskId`、`runtime.remoteToolInputs` 等 Runtime 内部 metadata，它们会被清理并由服务端重建。

## GetTask

使用服务端返回的 Task ID 查询当前任务：

```json
{
  "jsonrpc": "2.0",
  "id": "get-task-001",
  "method": "GetTask",
  "params": {
    "id": "task-approval-001"
  }
}
```

注意 `GetTask` 使用 `params.id`，不是 `params.taskId`。响应中的 Task 结构与 `SendMessage` 的 `result.task` 相同。

## 客户端实现检查表

- REST 多轮请求始终复用 `conversation_id`；不要向 REST Query 请求添加 A2A `taskId`。
- A2A 中断恢复同时复用 `contextId` 和 `taskId`。
- 并行工具恢复从 `_interrupt.items[].toolCallId` 读取关联 ID，并写入对应 `parts[].metadata.toolCallId`。
- SSE 按事件逐条解析，以终态 `statusUpdate` 判断 A2A Task 是否结束。
- A2A 输出按 `TextPart`、`DataPart`、`FilePart` 分类型处理。
- 标量最终答案读取 `parts[].text`；结构化中间事件和结构化最终结果读取 `parts[].data`。
- JSON-RPC 顶层 `id`、A2A `taskId` 和函数工具 `toolCallId` 不可混用。
